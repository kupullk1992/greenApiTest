# WhatsApp × GREEN-API

Веб-клиент для обмена текстовыми сообщениями WhatsApp через GREEN-API. Выполнен в рамках тестового задания

## Возможности

- Подключение по `apiUrl`, `idInstance` и `apiTokenInstance` с проверкой состояния и настроек инстанса.
- Создание личного чата по номеру телефона в международном формате.
- Работа с несколькими чатами в текущей сессии.
- Отправка и получение текстовых сообщений, включая emoji и ссылки.
- Отображение состояния отправки, доставки, прочтения и ошибок.
- Автозаполнение последнего корректного адреса API.
- Адаптивный интерфейс для настольных и мобильных экранов.

## Технологии

React, TypeScript, Vite, Fetch API и CSS
Для проверки кода Vitest, jsdom, ESLint и Prettier.

## Локальный запуск

Требования: Node.js 22.13+ или 24+ и npm.

```sh
npm install
npm run dev
```

После запуска приложение доступно по адресу, указанному Vite в терминале. По умолчанию — `http://127.0.0.1:5173`.
Альтернативная установка через pnpm с зафиксированными зависимостями:

```sh
pnpm install --frozen-lockfile
pnpm dev
```

## Настройки GREEN-API

Для работы необходим авторизованный WhatsApp-инстанс. Значения `apiUrl`, `idInstance` и `apiTokenInstance` берутся из его параметров в личном кабинете GREEN-API.

Получение сообщений реализовано через HTTP API. Для этого адрес webhook должен быть пустым, а уведомления — включены:

```json
{
  "webhookUrl": "",
  "incomingWebhook": "yes",
  "outgoingAPIMessageWebhook": "yes",
  "outgoingMessageWebhook": "yes",
  "outgoingWebhook": "yes",
  "stateWebhook": "yes"
}
```

Приложение проверяет настройки при подключении и сообщает о недостающих параметрах. Автоматическое изменение настроек инстанса не выполняется. После их изменения требуется дождаться применения на стороне GREEN-API.

## Архитектура

```text
src/
  api/          HTTP-клиент, проверка ответов и контракты GREEN-API
  components/   формы подключения, список чатов и переписка
  hooks/        управление сессией переписки и жизненным циклом polling
  model/        reducer, обработка уведомлений и цикл очереди

  config.ts     ограничения интерфейса
  types.ts      общие типы сессии и обработчиков
```

### Создание чата и отправка

Метод `CheckWhatsapp` проверяет наличие аккаунта по номеру и возвращает идентификатор чата. Номер передаётся строкой через поле `chatId`, чтобы избежать потери точности. Поддерживаются идентификаторы `@lid` и `@c.us`; связанные идентификаторы сопоставляются в пределах сессии. Для старого формата ответа только с `existsWhatsapp` используется идентификатор `номер@c.us`.

Отправляемое сообщение сразу появляется в переписке. После ответа `SendMessage` оно связывается с `idMessage`. Последующие уведомления обновляют существующую запись. Принятие сообщения API отображается отдельно от доставки получателю.

Если ответ отправки потерян, попытка сохраняется со статусом «Не удалось подтвердить отправку». Пришедшее позже уведомление без установленной связи по `idMessage` отображается отдельно: сопоставление по тексту и времени не выполняется, поскольку одинаковые сообщения могут быть отправлены намеренно. Повторная отправка может создать ещё одно сообщение.

### Получение сообщений

Уведомления обрабатываются одним последовательным циклом:

```text
ReceiveNotification → обработка события → DeleteNotification
```

Удаление подтверждается только после обработки; проверяются HTTP-статус и поле `result`. Сетевые ошибки вызывают повторные попытки с увеличивающейся задержкой. При отключении запросы и ожидания отменяются через `AbortController`.

При неоднозначном результате удаления повторно проверяется начало очереди. Если прежний `receiptId` остался, удаление повторяется без повторной обработки события. Если очередь продвинулась, полученное новое уведомление сохраняется и обрабатывается перед следующим запросом получения. Бизнес-ошибки с HTTP 200 также распознаются; `INVALID_PARAM` останавливает цикл с сообщением о настройках инстанса.

Повторные сообщения объединяются по идентификаторам. Статус, полученный до ответа отправки, сохраняется и применяется после сопоставления. Запоздалое событие не понижает статус прочитанного сообщения.

Неподдерживаемое содержимое отображается заглушкой и подтверждается. Неизвестные служебные события пропускаются. Повреждённое поддерживаемое событие останавливает обработку без удаления из очереди.

## Хранение данных и ограничения

- Чаты, сообщения, ID инстанса и токен хранятся в памяти текущей сессии. Перезагрузка или выход очищают сессию; загрузка прежней истории не реализована.
- В `localStorage` сохраняется только последний корректный `apiUrl`. Недоступность хранилища не блокирует подключение.
- Лимит текста в интерфейсе — 4000 символов. Проверка номера соответствует диапазону `CheckWhatsapp`: 11–16 цифр с кодом страны.
- Файлы, звонки и управление группами не входят в реализованный функционал.
- При неизвестном результате отправки автоматический повтор не выполняется, поскольку сервер мог уже принять сообщение.
- Очередь инстанса общая для всех потребителей. Одновременная работа нескольких вкладок или клиентов не координируется.
- Редкая смена LID во время сессии не отслеживается.

## Безопасность и доступность API

Параметры подключения вводятся пользователем и не включаются в исходники или переменные окружения сборки. Токен не записывается в браузерное хранилище. Приложение не добавляет URL запросов и сырые ответы API в свои сообщения об ошибках или логи.

Авторизация GREEN-API передаёт токен в URL запроса, поэтому он доступен в DevTools браузера. Поле ввода токена скрывает его на экране, но не защищает от доступа расширений браузера. Используются HTTPS, `no-store` и `no-referrer`.

Прямые запросы требуют поддержки CORS для GET, POST и DELETE на выбранном API-хосте. Реальная отправка и получение ответа проверены локально с WhatsApp-инстансом. Работа с другого домена зависит от настроек CORS и доступности GREEN-API. При размещении используется каталог `dist`; при отсутствии CORS потребуется серверный посредник.
